# 部署内存占用（实测）

全部数字来自实测，不是估算。测量脚本在 `tools/measure_memory.py`，你可以自己跑一遍。

机器：Windows 10/11 · Node v24.21.0 · Python 3.12.14 · numpy 2.3.5

---

## 一句话结论

**一个 512 MB 内存的 VPS 跑得动，但并发高时会紧张；1 GB 很舒服，2 GB 随便用。**

常驻内存约 **110 MB**（两个服务），另有每次请求短暂 spawn 的 Python 进程（峰值 36~47 MB，用完即退）。

---

## 一、常驻部分（两个 Node 服务）

| 服务 | 刚启动 | 空闲 20 秒 | 处理 20 个请求后 |
|---|---|---|---|
| 蜘蛛 UI（4317） | 54.8 MB | 53.5 MB | — |
| 量化看板（4400） | 55.0 MB | 53.3 MB | 68.2 MB |
| **合计** | **109.8 MB** | **106.8 MB** | **121.7 MB** |

量化看板会长一点，因为有请求结果缓存（默认 TTL 20 秒）。实测长时间运行后稳定在 ~130 MB。

### ⚠️ 别被「虚拟内存 5.3 GB」吓到

任务管理器里 Node 进程的**虚拟内存显示 5.3 GB**，这是 **V8 预留的堆地址空间上限**，不是实际占用：

```
heap_size_limit  : 4288.0 MB    ← V8 的堆上限（预留的地址空间）
used_heap_size   :    4.8 MB    ← 真正用掉的堆
heap_total       :    6.3 MB    ← 已向 OS 申请的堆
RSS              :   48.1 MB    ← 实际物理内存
```

虚拟内存是**记账**，物理内存（RSS / 工作集）才是**占用**。
容器里如果设了内存 limit，看的是 RSS，不会被虚拟内存撑爆。

## 二、临时部分（每次请求 spawn 一个 Python 进程）

这是架构决定的：`server.mjs` 用 `execFile` 调 Python 跑一次管道，
**算完就退出**，所以内存是瞬时的，不累积。

| 场景 | 根数 | 纯算（指标） | 完整管道* |
|---|---|---|---|
| 小请求 | 500 | 35.4 MB | 35.8 MB |
| 常规 | 2000 | 36.1 MB | 40.0 MB |
| 大请求 | 5000 | 38.0 MB | 47.1 MB |
| 很大 | 10000 | 41.0 MB | — |

\* 完整管道 = 27 个指标 + 5 个策略 + 5 次回测 + JSON 序列化

**基线是 35.7 MB**（Python 解释器 + numpy 的空载），所以：

- 数据量从 500 涨到 10000 根（**20 倍**），内存只从 35.4 涨到 41.0 MB（**+16%**）
- 每根 K 线约 **0.5 KB**
- 增量很小，因为大头是解释器和 numpy 本身

### 参数优化（最重的一次请求）

| 根数 | 参数组合 | 峰值 |
|---|---|---|
| 500 | 20 | 37.7 MB |
| 1000 | 60 | 37.4 MB |
| 2000 | 100 | 38.8 MB |
| 2000 | 300 | 39.1 MB |

**300 组参数也只比基线高 3.4 MB** —— 因为优化器每算完一组就把中间对象释放了，
不把所有组合的结果同时留在内存里（只留评估结果，每组几十字节）。

### 并发

同时打 8 个不同标的的请求：

```
全部返回，用时 3644ms
Python 进程总峰值  95.8 MB     ← 约 2~3 个进程同时在跑
Node  进程总峰值 371.6 MB      ← 含其他 Node 进程
```

**关键**：8 个并发请求下 Python 总峰值只有 ~96 MB，
说明 Node 侧在**排队**而不是一次性 spawn 8 个进程。
（`execFile` 没有并发上限控制，这是被测数据源响应时间自然形成的节流。）

极端情况估算：如果 8 个进程真的同时启动，`8 × 47 = 376 MB`。
实际不会到这个量级，但**给 512 MB 的机器要留意**。

## 三、按部署场景推荐

| 场景 | 建议内存 | 说明 |
|---|---|---|
| **Docker 容器（最小）** | **256 MB** | 两个服务 110 MB + 单个 Python 峰值 47 MB + 余量。够跑，但只适合单人低频用 |
| **1 GB VPS** | **512 MB ~ 1 GB** | 舒服。能扛几个并发，也能跑优化器 |
| 多人共用 / 频繁优化 | **1 ~ 2 GB** | 并发 + 大参数搜索有余量 |
| 本机开发 | 无所谓 | 实测这台机器总内存 15.6 GB |

### 别忘了操作系统本身

上面只是**应用**的占用。整机还要加上：

| 系统 | 空载占用 |
|---|---|
| 精简 Linux 容器（alpine/debian-slim） | 50 ~ 150 MB |
| 完整 Linux 服务器 | 200 ~ 500 MB |
| Windows Server | 1.5 ~ 2 GB |

**所以 512 MB 的 VPS 跑 Linux 没问题，跑 Windows 是不可能的。**

## 四、怎么进一步省内存

如果非要在 256 MB 里跑，按性价比排序：

1. **调小默认 K 线根数** —— 500 → 2000 只差 4 MB，不是瓶颈，但配合下面几条有用
2. **限制并发** —— 给 `quant/server.mjs` 加个请求队列（目前没有）。这是唯一真实的并发风险点
3. **缩短缓存 TTL** —— 缓存的是 JSON 字符串，5000 根约 2.5 MB/条。TTL 长 + 标的杂会累积
4. **`--max-old-space-size=128`** —— 限制 V8 堆。实测只用了 4.8 MB，128 MB 绰绰有余，还能防止内存泄漏失控
5. **别同时开蜘蛛 UI** —— 它占 54 MB，而且和量化功能无关

## 五、复现测量

```bash
# 内存占用（合成数据，不联网，几秒完成）
python tools/measure_memory.py
```

这个脚本用**父进程测子进程**的方式拿峰值工作集 ——
进程内自测（ctypes + GetProcessMemoryInfo）在 Windows 上会返回 0，不可靠。

用**合成数据**而不是真实行情：内存取决于「根数 × 组合数」，与数据来源无关，
所以合成数据能把这两个变量单独拉出来看，而且不用联网等几秒。

另外它也做了完整性回归：`compute()` 的内存应该随根数**线性**增长。
如果哪天某处不小心把中间结果全留下来，`5000 根` 那行的「每根 KB」会突然跳一个数量级。

### 想看真实请求的端到端峰值

```bash
python tools/measure_memory.py   # 合成数据只测计算部分
```

真实端到端（含联网拉取与 JSON 序列化）可以直接用系统工具观察，或者：

```powershell
# Windows：一边打请求一边采样子进程峰值
while ($true) {
  Get-Process python -EA SilentlyContinue |
    Measure-Object WorkingSet64 -Maximum |
    ForEach-Object { "Python 峰值: {0:N1} MB" -f ($_.Maximum/1MB) }
  Start-Sleep -Milliseconds 200
}
```

## 六、这些数字的局限

诚实说明：

- **在 Windows 上测的**。Linux 上 Python/Node 的常驻内存通常**略低**（glibc vs MSVCRT、页大小不同），
  但不会有数量级差异。
- **合成数据的 JSON 大小与真实接近**（5000 根约 2.5 MB），
  但真实数据有中文字段名，序列化后的实际字节数可能略高。
- **没有长期运行测试**。最长的观察是 78 分钟（蜘蛛 UI 48.4 MB，无明显增长）。
  如果怀疑内存泄漏，需要挂几天看趋势 —— 这件事**没做**。
- **Docker 没实测**（本机没有 docker），所以容器里的实际占用是**推断**，
  基础镜像本身的占用没量过。
