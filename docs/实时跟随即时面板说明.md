# 让 Prompt Spider 跟着 Agent 一直跑

> 目标：把「播完就停的动画」变成**持续跟随 Agent 的实时面板**。
> 状态：**已实现并验证**，当前正在运行中。

---

## 一、绑定到底是怎么发生的

「Agent 的可视化怎么和 Agent 绑定」——有三条路，成本完全不同：

| 方式 | 谁推动 | Agent 要不要配合 | 实际效果 |
|---|---|---|---|
| **A. 手动上报** | Agent 主动调 MCP 工具 | ✅ 要（每步都要） | 精确，但 Agent 一忘就断，且多一层开销 |
| **B. 日志尾随** | 外部进程读会话日志 | ❌ **不要** | 完整、自动、零侵入 —— **当前用的就是这个** |
| **C. 拦截工具调用** | 包一层代理 | 要改调用链 | 侵入性太强，没有必要 |

**B 是正解**，原因很简单：DSH 本来就把每一次工具调用、每一步、
每一次人工授权都写进会话日志了。**再让 Agent 重复上报一遍是浪费**，
而且会漏（Agent 忙于干活时会忘）。

所以这里的关键设计是：

> **可视化不需要 Agent 知道它存在。**
> Agent 只管干活 → 日志自动写 → 喂养器读日志 → 画布自动画。

---

## 二、完整链路

```
  ① Agent 干活
     ↓  每调用一次工具、每完成一步，DSH 自动写日志
  ② ~/.dsh/sessions/<工作区>/<会话id>/session.v4.jsonl.zstd
     ↓  多帧追加式 zstd（必须逐帧解压，见下文陷阱）
  ③ mcp/live-feed.mjs
     ↓  每 2 秒轮询：增量读新帧 → 解析成事件 → 分类到三条分支
     ↓  通过 MCP client 调 spider_update_events
  ④ MCP hub（随机端口 + token）→ 提供 previewUrl
     ↓  publishSession() 写入发现文件
  ⑤ lib/live-sessions.json
     ↓  /api/live-status 补上「进程是否还活着」
  ⑥ http://127.0.0.1:4317/live   ← 稳定入口，永远指向当前有效会话
```

**为什么需要 ⑤ 和 ⑥ 这两层**：MCP hub 每次启动都换随机端口
（49909 → 62664 → 65221…），旧链接会指向已经死掉的会话，
页面停在最后一帧不动 —— 看起来像「没有新动画」，其实代码没问题。
所以有了**发现文件 + 稳定入口页**，你只需要记 `/live` 一个地址。

## 三、启动：一条命令

**双击 `实时跟随.cmd`** —— 它会：

1. 需要的话自动拉起 4317 主服务（已经跑着就跳过，不会 EADDRINUSE）
2. 启动喂养器，跟随**最近修改的那个会话**
3. 自动打开 http://127.0.0.1:4317/live

**保持窗口开启 = 持续跟随。** Ctrl+C 结束会把会话标记完成，历史可循环回看。

手动启动也行：
```powershell
node mcp/live-feed.mjs --interval 2.5          # 跟随最近修改的会话
node mcp/live-feed.mjs --session <id>          # 指定会话
node mcp/live-feed.mjs --no-discover           # 不写发现文件（不想暴露 token 时）
```

## 四、状态是**真的**吗（这一节容易被糊弄）

`/live` 页曾经只看「发现文件的最后写入时间」来判活跃 —— 这是错的：

> 喂养器被 kill 后，条目还在、`updatedAt` 还很新，
> 页面显示「活跃」，但链接指向已经死掉的会话。

实测踩到过：发现文件里留着 `pid 4676 / port 53507` 的条目，
进程早就没了，端口也关了。

现在有两道保险：

1. **`/api/live-status`** 用 `process.kill(pid, 0)` 检查进程**真的**还活着
   （信号 0 不发信号，只做存在性检查），返回 `alive` / `probe` 字段
2. **`publishSession()` 发布时按 pid 存活清理**，死条目直接删掉

页面上：

| 显示 | 含义 |
|---|---|
| 绿点「跟随着 · 修改文件」 | 进程活着，正在跟，`修改文件` 是当前动作 |
| 黄点「已停止（喂养器进程已退出）」 | 进程没了，卡片标灰、按钮不可点 |

## 五、数据源在哪（这段最值钱，别再走弯路）

DSH 有**三处**会话数据，只有一处是完整事件流。三处都试过：

| # | 位置 | 内容 | 能否用于实时 |
|---|---|---|---|
| 1 | `storages/session_projcache/sessions/*.json` | UI 状态缓存：`todos` / `turnOutline` / `sessionStats` | ⚠️ **部分可用** |
| 2 | `sessions/<...>/<id>/session.v4.jsonl.zstd` | **完整事件流** | ✅ **正确数据源** |
| 3 | 同上，但整体解压 | 只能拿到第一帧 | ❌ 不可用 |

### 为什么 #1 不够用

`turnOutline.val.turns[].response` 是**截断预览**（约 120 字）。靠它做分类，信号极弱。

为此写坏了两版启发式：

| 版本 | 规则 | 结果 |
|---|---|---|
| v1 | 有 `prompt` 就归 `you` | **30/32 全归 you** —— 分支失衡 |
| v2 | 关键词命中 | **29/32 全归 code** —— 又翻到另一头 |

两次都失败，根本原因是**数据本身被截断了**，再怎么调规则都是猜。

### #2 才是对的，但有个陷阱

那个 zstd 文件是**多帧追加式**的：

```javascript
// ❌ 这样只解出第一帧（244 字节的会话头）
zstdDecompressSync(readFileSync(file))

// ✅ 必须按魔数拆帧，逐帧解压
const MAGIC = [0x28, 0xB5, 0x2F, 0xFD];
// 实测该文件 3135 个帧 -> 解出 16.59 MB / 4980 条记录
```

**不拆帧的后果**：文件看着 4.56 MB，解出来只有 244 字节，你会以为"日志不存内容"。

拆帧后拿到的事件类型：

```
 789  tool/result        772  tool/call          ← 含真实工具名
 752  session-log-deepseek
 751  step/start         750  step/end           ← 可做进度
 750  assistant/message
  75  user/message        32  turn/start  31  turn/end
  24  approval/asked      23  approval/decided   ← 真实的人工介入信号
  18  workspace/changes
```

每条是 `{type, seq, time, data}`，例如：

```json
{"type":"tool/call","seq":21,"time":1791897717042,
 "data":{"turn":1,"step":1,"callId":"call_00_...","name":"web_search","arguments":"{...}"}}
```

## 六、分流依据：用真实工具名，不猜

有了 `tool/call` 的 `name` 字段，分类才有真实依据：

| route | 判据 | 工具示例 |
|---|---|---|
| **you** | 该轮次出现过 `approval/asked` | 提请人工授权（沙箱升级、写工作区外文件…） |
| **model** | 主导工具是委派类 | `subagent` / `subagent_fork` / `workflow` / `spawn_teammate` / `team_task_*` / `wait_agent` |
| **code** | 其余全部 | `read` / `grep` / `glob` / `pwsh` / `edit` / `write` / `present` / `todo_write` / `mcp__rea__*` |

**为什么 `you` 用 `approval/asked` 而不是关键词**：那是**真实发生过的人工介入事件**，
不是从文字里猜的。这是最硬的信号。

实测分布（某次会话 32 轮）：**code 19 / model 1 / you 12** —— 三支都有，不再是 30:1:1 那种失衡。

## 七、实现要点

### 增量读取，不重复解压

每轮重解 16 MB 会很慢。`EventLogReader` 记住：

- `bytePos` —— 已稳定消费到的字节位置
- 只解新出现的帧
- **保留最后一帧不消费** —— 它可能正在写入

### 心跳：让面板"在动"

即使当前轮次没结束，副标题也会持续刷新真实进度：

```
32 轮 · 782 步 · 当前 job_output
```

`steps` 由 `tool/call` 计数，`当前 X` 是最近一次工具调用名。
**这就是"一直运行"的体感来源** —— 面板永远显示 Agent 正在干什么。

### 标签

- 创建会话时用**第 1 轮**的 `user/message` 文本作为会话名
- 之后的「当前动作」用最近一次工具调用名单独显示

⚠️ 长会话里标题会显得过时：比如这个会话第 1 轮是「调研 REA 项目」，
后来一直在做量化界面。**标题是会话身份，不随任务变** ——
真正该看的是「当前」那一栏。这是刻意的，不是 bug。

## 八、命令行参数

| 参数 | 说明 |
|---|---|
| `--interval 2.5` | 轮询间隔（秒），默认 1.5 |
| `--max 180` | 画布窗口内最多几步 |
| `--session <id>` | 指定会话，默认自动选最近修改的 |
| `--verbose` | 打印每条同步明细 |
| `--no-discover` | 不写发现文件（token 不落盘） |

## 九、已知限制

1. **标签里可能混入运行时提示**
   比如 `Time sampled while preparing turn N, step M: ...` 和
   `Current runtime context. ...` —— 这些是 DSH 注入到 user 消息里的系统文本，
   会被当作用户提问的一部分。可以加过滤规则去掉。

2. **`model` 偏少是真实的，不是 bug**
   大多数轮次一个人就能做完，很少开子代理，所以 `model` 可能只有 1。
   分类反映的是**实际发生的事**，不该为了分布好看而调整。

3. **只能跟一个会话**
   默认自动选最近修改的。同时跑多个会话需要加 `--session` 起多个实例。

4. **依赖 DSH 内部存储格式**
   如果 DSH 升级改了 `session.v4.jsonl.zstd` 的结构或存储路径，
   脚本需要同步调整。已经写明了所有路径和魔数，改起来不难。

5. **发现文件是个信息暴露点**
   `lib/live-sessions.json` 里写着带 token 的预览地址，本机任何进程都能读到。
   这是本地单机演示工具（只监听 127.0.0.1），token 只能看不能改数据，
   所以风险可接受。不想落盘就加 `--no-discover`。
